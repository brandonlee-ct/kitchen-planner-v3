## Why this exists — both defects gate H's next action

1.18 shipped dormant and correct in the happy path. Two defects only bite the moment H
populates `planner.component_skus`, which is exactly what runbook R4 tells H to do next.
Neither is a crash: **both quietly produce a wrong number and report success**, which is
the worst failure mode for a feature that charges customers.

### Defect (a) — `parseComponentSkus` invents quantities

O ruling 4 (RELAY.md, 1.18 entry) is explicit: *"an explicit `qty: 0` is skipped, not
floored to 1 … inventing a quantity is the same fabrication ruling 3 forbids."* The
implementation honours that for `0` and negatives and then breaks it for everything else:

| `qty` in the metafield | Today | Correct |
|---|---|---|
| absent / `null` / `""` | `1` | `1` — keep. A merchant who omits it means one |
| `2` or `"2"` | `2` | `2` — keep |
| `0`, `-2` | skipped + warn | skipped + warn — keep |
| `0.4` | **`1`** — invented, **overcharges** | skipped + warn |
| `2.7` | **`2`** — silently floored | skipped + warn |
| `"two"`, `{}`, `[]` | **`1`** — invented, silent | skipped + warn |
| `Infinity`, `NaN` | **`1`** — invented, silent | skipped + warn |
| `true` | **`1`** — `Number(true)` is 1 | skipped + warn |

The `0.4 → 1` case is the sharpest: it is *precisely* the silent overcharge ruling 4 was
written to prevent, and it slips through because the guard tests `qtyNum <= 0` before the
floor rather than testing that the value is a whole number at all. Every wrong row above
is also **silent** — no `console.warn` — so H would have no signal.

### Defect (b) — the audit tool's resolved-set does not match the runtime's

`runCatalogueAudit` builds `allFetchedVariantIds` from **every fetched node, drafts
included**. The runtime resolves components through `getComponentVariantIndex()`, which is
built from `products` — and `loadShopifyProducts` filters `(Draft)` titles out of
`products`. The two sets are therefore different by exactly the drafts.

Consequence: a component variant that belongs to a Draft product reads **`OK`** in
`?catalogaudit=1` and then, at runtime, resolves to nothing — rendering as
`Unknown component (gid://…)` at **$0.00**, and going to `cartCreate` anyway, where
Shopify's `userErrors` for one unavailable line fails **the entire cart** (1.18 risk 2).
On a catalogue where roughly 38 of 53 products are Draft, this is the likely case, not
the edge case. R4 step 4 instructs H to trust that `OK`. A falsely-reassuring audit is
worse than no audit at all.

## Task (one deliverable)

Make `parseComponentSkus` refuse to invent a quantity, and make the audit tool's
component resolution use the same set of products the planner actually resolves against —
reporting drafts and skipped entries distinctly.

## In scope — `main.js` only (locate by symbol; do NOT cite line numbers)

1. **`parseComponentSkus`** — replace the quantity block with the table above as one
   statable rule: *if `qty` is absent, default to 1; if `qty` is present it must be a
   whole number of 1 or more, and anything else is skipped with a named
   `console.warn`.* `Number.isInteger()` after a numeric coercion covers `NaN`,
   `Infinity`, fractions and booleans in one test. Keep the existing missing-`variantId`
   skip, the malformed-JSON `[]` degradation, and the function's signature and name.
2. **`runCatalogueAudit` / `auditComponentSkus`** —
   - Replace the `allFetchedVariantIds` Set with an index that also records whether the
     owning product's title matches `/\(Draft\)/i` — the *same* test
     `loadShopifyProducts` uses. Do not re-derive "draft" any other way; if the two
     tests ever diverge the bug comes straight back.
   - Classify each parsed component as resolved / **unresolved** (no fetched variant) /
     **draft-parent** (fetched, but its product is a Draft, so the runtime will not
     resolve it).
   - Report **skipped** entries too — raw array length minus parsed length — so a `qty`
     the parser rejected is visible to H instead of vanishing.
   - Return structured counts and build the status string from them. Do **not** keep
     deriving counts by string-sniffing `status.indexOf('unresolved')`; that is what
     makes the summary line fragile as soon as the wording changes.
   - Keep `component_skus_status` and `component_skus_count` as keys, keep `absent` /
     `unparseable` / `OK` spelled exactly as they are today (R4 step 4 quotes them), and
     express problems as `OK (…)` — the pattern R4 already documents. Any new key goes
     **after** every existing key so no pre-existing column shifts position.
