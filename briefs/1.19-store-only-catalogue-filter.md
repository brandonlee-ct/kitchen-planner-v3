## 1. The problem (A's statement, verified at file level)

H's product model (`UNIT-SKU-PLAN.md` §1) has three kinds of SKU:

1. **Cabinets** — a complete cabinet, carcase and legs and hinges and fronts, one price.
2. **Companions** — benchtop, sink, oven, hob: their own SKUs, placeable/attachable.
3. **Spare parts** — hinges, panels, legs sold separately as extras and replacements.
   These are **store-only**: they must **never** appear in the planner.

The planner renders **every** Storefront-published product that is not titled `(Draft)`.
`renderProductPanel` groups everything in `products` by `productType` and renders all of
it; there is **no category filter anywhere in the load path**. The only exclusion is the
`(Draft)` title test in `loadShopifyProducts`. So the moment H publishes a hinge for U0, it
appears in the catalogue as a placeable item with a placeholder box and a made-up
`600×720×580` size — because the fallbacks exist precisely to render a product with no
`planner.*` data.

`UNIT-SKU-PLAN.md` §3 previously claimed this was already handled "via `planner.category`
… No code change needed". That was wrong and has been corrected. This brief builds the
mechanism.

## 2. Category value convention — proposal to H (Law H: recommendation + default)

`planner.category` today carries `base` / `wall` / `tall` / `corner` / `island` (placement
behaviour, via `getPlacementCategory`) and `service` (quote-only, 1.17).

**O recommends: `store-only`.** Implemented as the default. Reasons:

- It names **the rule** ("never show this in the planner"), not the product type. It
  therefore also covers anything else non-placeable H may add later — gift cards, sample
  chips, delivery fees, warranties — without inventing a second convention.
- `part` / `parts` would collide with a plausible near future: Track 6 U2 makes companion
  SKUs attachable, and a handle or a hinge could legitimately become a *slot companion*.
  A category meaning "is a part" would then have to mean two opposite things.
- `spare` is too narrow, `hidden` does not say hidden from whom, and `accessory` describes
  things that may well be placeable.
- It is self-documenting in Shopify Admin: H reading `store-only` on a metafield knows
  exactly what it does.

**H can override with one line.** The value lives in a single `Set`
(`STORE_ONLY_CATEGORIES`), so a different word is a one-word change, and more than one
value can be accepted at once during a data migration. The read is normalised
(`trim().toLowerCase()`), so `Store-Only` or a trailing space in Shopify Admin still works
— that class of silent mismatch is exactly how a hinge would reach the catalogue.

## 3. Acceptance criteria (A's, verbatim intent)

| # | Criterion |
|---|---|
| a | A product marked store-only **never** appears in the catalogue panel — desktop **or** touch |
| b | It **still** resolves with its real name and price when referenced in `component_skus` — filter the display, not the data |
| c | Everything not marked store-only behaves **exactly** as today |
| d | The audit tool shows store-only status so H can verify the data |
| e | The "how to test" note starts with how to get the build on screen (Law L) |

## 4. In scope — `main.js` only

1. **`STORE_ONLY_CATEGORIES`** — a module-level `Set`, default `['store-only']`, declared
   **before** `runCatalogueAudit` and `renderProductPanel` in source order.
2. **`isStoreOnlyCategory(value)`** — normalise (`String`, `trim`, `toLowerCase`) and test
   membership. **One helper, used by every caller**, so the panel and the audit tool can
   never disagree about what store-only means.
3. **`isStoreOnlyProduct(product)`** — thin wrapper over the helper for the runtime's
   `product.category`.
4. **`renderProductPanel()`** — filter to placeable products **before** grouping; drive the
   existing "No products available." empty state off the filtered length so a
   fully-store-only catalogue does not render a blank panel; log one summary line when
   anything is hidden, so it is verifiable on an iPad through eruda without DevTools.
5. **`runCatalogueAudit`** — one `store_only` column, appended **after** every existing key
   so no pre-existing column shifts, plus one summary count line. The audit must derive
   store-only from the **same effective category** the runtime uses (`categoryApplied`,
   i.e. `planner.category` falling back to `productType`), through the shared helper.

## 5. Out of scope / do NOT touch — and one trap

- ⛔ **Do NOT add a guard to `placeProduct`.** It looks like the obvious belt-and-braces
  and it would **destroy customer data**: `loadScene` restores every saved item by calling
  `placeProduct(product, true)`. A store-only guard there would silently drop items from
  any project saved before the filter existed, breaking the standing "cabinets sit on the
  300mm slab after save → reload" regression check and losing part of a customer's design.
  A's criterion is deliberate — **filter the display, not the data.**
- **No change needed for auto-design** (verified, not assumed): `auto-design-rules.js`
  `findBaseProduct` / `isCornerProduct` both require `p.category === 'base'`, so a
  `store-only` product can never be selected by the solver. The wizard only reads
  `products.length`.
- Do not touch `products` population, `shopifyNodeToProduct`, `PRODUCTS_QUERY`,
  `getComponentVariantIndex`, `resolveComponentLines`, the quote/CSV/PDF/cart paths,
  `scene_json`, Supabase, `index.html`, `style.css`, or any existing audit column.
- No function signature changes. No refactor of working code. No new CSS breakpoints.

## 6. Definition of Done

- With a store-only product in the catalogue: absent from the panel on desktop **and** at
  390px touch width; still resolvable by name and price as a `component_skus` entry;
  `?catalogaudit=1` shows it with `store_only: YES`.
- With **no** store-only product: the panel, the quote, and every pre-existing audit
  column and count are byte-for-byte what they were before this change.
- `npm run build` passes; reviewer subagent run; "how to test" note included.
- `TASKS.md` updated; the board goes **⏳ on push, ✅ only after H live-verifies**.

## 7. How to test (Law L — starts with getting the build on screen)

1. **Get the build on screen.** `git fetch && git checkout cursor/1-19-store-only-filter-and-c8-audit-fixes-9814 && npm install && npm run dev`, then open the printed URL (normally `http://localhost:5173/`). On the live site instead, wait for Vercel to deploy `main` after the merge and open `https://planner.brownboxkit.co.nz`.
2. **No-op check first.** With today's catalogue (no product marked store-only) the panel
   must be identical to before: same groups, same products, same badges.
3. **Set one product store-only** — in Shopify Admin set `planner.category` to
   `store-only` on one published test product (or, for a local-only check, stub the
   Storefront response). Reload the planner.
   *Success looks like:* that product is gone from the catalogue panel; everything else is
   unchanged.
4. **Audit check.** Open `?catalogaudit=1` → Console → `🗂️ Catalogue audit` group. The
   table shows `store_only: YES` on that product's row and `—` on the rest, and the
   summary reports the count.
5. **Component-resolution check (criterion b).** Reference that store-only product's
   variant in another product's `planner.component_skus`, place the parent, and open the
   quote: the component line must show the **real name and price**, not
   "Unknown component … $0.00".
6. **Touch check.** Repeat step 3 on an iPad/iPhone (or a 390px-wide window). The panel is
   rendered once for both input paths, so the same list is what touch sees — confirm it.
7. Run the `AGENTS.md` post-task smoke checklist, desktop **and** touch.
